## EXP-01: macOS 카메라 입력 확인 및 파란색 영역 탐지

- **상태:** 카메라 입력 문제 해결 및 기본 탐지 구현 완료
- **실험 날짜:** 2026-11-05
- **목적:** Mac 내장 카메라에서 실시간 프레임을 받아오고, 화면 속 파란색 영역을 탐지해 위치를 표시하는 최소 기능을 구현한다.
- **질문 / 문제:** OpenCV에서 카메라를 열 수 없거나, 카메라 연결은 성공한 것처럼 보이지만 실제 프레임을 가져오지 못하는 문제가 발생했다.
- **초기 가설:** macOS 카메라 권한 또는 OpenCV의 카메라 장치 인덱스 설정이 원인일 수 있다.
- **환경 및 데이터:** macOS, MacBook 내장 카메라, Python 3.10.13 가상환경(.venv), OpenCV, NumPy. 카메라 앞에 파란색 물체를 두고 테스트했다.
- **변경한 변수:** 카메라 접근 권한을 확인하고, OpenCV 카메라 인덱스를 0부터 확인했다. 이후 macOS용 AVFoundation 백엔드를 명시해 인덱스별 프레임 수신 여부를 비교했다.
- **ChatGPT의 제안:** macOS의 개인정보 보호 및 보안 설정에서 실행 앱의 카메라 권한을 확인하고, Photo Booth에서 카메라 자체가 작동하는지 확인한 다음, 간단한 코드로 `isOpened()`와 `read()` 결과를 각각 검사한다. 이후 인덱스 0~4를 순서대로 테스트한다.
- **직접 수행한 작업:**
  1. 최초 실행에서 카메라 접근 권한 관련 메시지(`not authorized to capture video`)와 초기화 실패를 확인했다.
  2. macOS 카메라 권한이 켜져 있는지 확인했다.
  3. Photo Booth에서 내장 카메라 영상이 정상적으로 나오는 것을 확인했다.
  4. `cap.isOpened()`와 `cap.read()`를 분리해 검사했다.
  5. 인덱스 0~4를 `cv2.CAP_AVFOUNDATION` 백엔드로 순서대로 테스트했다.
  6. 인덱스 1에서 실제 프레임이 들어오는 것을 확인했다.
- **관찰한 결과:**
  - 첫 실행에서는 `OpenCV: not authorized to capture video`가 출력되고 카메라를 열지 못했다.
  - 권한 확인 후 Photo Booth에서는 카메라가 정상 작동했다.
  - 인덱스 0은 `cap.isOpened() == True`였지만 `cap.read() == False`였다.
  - 인덱스 1은 연결 및 프레임 수신에 성공했고, 프레임 크기는 `(1080, 1920, 3)`으로 확인됐다.
  - 인덱스 2~4는 장치 범위를 벗어나 초기화에 실패했다.
  - 최종적으로 `cv2.VideoCapture(1, cv2.CAP_AVFOUNDATION)`를 사용해 카메라 프레임을 가져올 수 있었다.
- **예상과 달랐던 점:** 인덱스 0에서 `isOpened()`가 True였기 때문에 영상도 정상적으로 읽을 수 있을 것으로 예상했지만, 실제 프레임 수신은 실패했다. 장치를 열었다는 사실만으로 프레임 수신까지 보장되는 것은 아니었다.
- **해석 및 한계:** `isOpened()`는 장치 열기 여부를 확인하고, `read()`는 실제 프레임을 읽었는지 확인한다. 두 검사는 서로 다른 단계다. 이 Mac 환경에서는 인덱스 1과 AVFoundation 조합이 정상 동작했다. 다만 인덱스 0이 내부적으로 어떤 장치 또는 스트림에 해당했는지는 로그만으로 확정할 수 없다. 실행 중 출력된 Continuity Camera 관련 경고는 있었지만, 인덱스 1에서 영상 프레임을 읽는 데 성공했으므로 해당 경고가 이번 실패의 직접 원인이라고 판단하지 않았다.
- **다음 단계:** 정상 프레임을 기반으로 HSV 색상 범위와 윤곽선 탐지를 적용하고, 파란색 물체를 화면에 표시한다.

## EXP-02: HSV 기반 파란색 영역 탐지 및 단일 영역 표시

- **상태:** 기본 기능 구현 및 실행 확인
- **실험 날짜:** 2026-11-05
- **목적:** 카메라 영상에서 파란색에 해당하는 픽셀을 분리하고, 탐지된 영역의 위치를 사각형과 중심점으로 시각화한다.
- **질문 / 문제:** 카메라 영상에서 특정 색상의 물체를 어떻게 찾아 화면 좌표로 표현할 수 있을까?
- **초기 가설:** HSV 색 공간에서 파란색 범위를 지정하면 해당 색상에 해당하는 픽셀을 분리할 수 있고, 연결된 픽셀 영역의 윤곽선을 이용해 물체의 위치를 계산할 수 있을 것이다.
- **환경 및 데이터:** Python 3.10.13, OpenCV, NumPy, Mac 내장 카메라, 파란색 물체.
- **변경한 변수:** BGR 원본 영상을 HSV로 변환하고, 파란색 HSV 하한·상한을 지정했다. 작은 영역 노이즈 제거와 최소 면적 조건을 적용했다.
- **ChatGPT의 제안:** `cv2.cvtColor`로 BGR을 HSV로 변환하고, `cv2.inRange`로 색상 마스크를 만든 뒤, Morphological Opening과 `findContours`를 이용해 영역을 추출한다. 가장 큰 윤곽선의 bounding box와 중심점을 표시한다.
- **직접 수행한 작업:** `project-b-vision/src/object_tracker.py`를 실행했다. 카메라 입력이 실패한 뒤 인덱스를 1로 변경해 다시 실행했고, 원본 영상 창과 색상 마스크 창이 표시되는 것을 확인했다.
- **관찰한 결과:**
  - 파란색 물체가 흰색으로 표시되고 나머지 영역은 검은색으로 표시되는 Color Detection 창이 나타났다.
  - 원본 영상 창에는 탐지된 영역을 둘러싼 초록색 사각형과 중심을 나타내는 빨간색 점이 표시됐다.
  - 색상 마스크와 원본 영상이 별도의 창으로 표시됐다.
  - 종료 키 입력은 영상 창이 키보드 포커스를 받고 있어야 정상적으로 감지될 수 있음을 확인했고, 이후 `q`와 ESC 입력을 종료 조건으로 사용하도록 코드를 조정했다.
- **예상과 달랐던 점:** 카메라 장치 인덱스 문제를 해결한 후에도 실행 중인 두 창이 각각 무엇을 보여주는지, 키보드 입력이 어느 창에 전달되는지 추가 확인이 필요했다.
- **해석 및 한계:** 색상 마스크는 파란색 물체만 의미적으로 인식하는 것이 아니라 지정한 HSV 범위에 들어오는 모든 픽셀을 흰색으로 표시한다. 따라서 파란색 조명이나 배경도 같은 조건을 만족하면 탐지 대상이 된다. 또한 현재 구현은 가장 큰 윤곽선 하나만 선택하므로 여러 파란색 영역을 동시에 표시하지 않는다.
- **다음 단계:** 중심점이 프레임마다 흔들리는 현상을 줄이고, 최근 위치를 연결해 움직임을 시각화한다.

## EXP-03: 중심점 평활화와 최근 이동 경로 시각화

- **상태:** 구현 및 여러 움직임 조건에서 실행 확인
- **실험 날짜:** 2026-11-05
- **목적:** 프레임마다 측정되는 물체 중심점의 작은 변화가 화면에서 크게 흔들려 보이지 않도록 보정하고, 최근 이동 궤적을 표시한다.
- **질문 / 문제:** 카메라 영상에서 계산한 중심점은 매 프레임 달라질 수 있다. 중심점의 흔들림을 줄이면서 물체가 이동한 경로를 화면에 보여주려면 어떻게 해야 할까?
- **초기 가설:** 이전 중심점과 현재 중심점을 가중 평균하면 갑작스러운 좌표 변화가 완화될 것이다. 최근 좌표를 제한된 개수만 저장해 선으로 연결하면 이동 경로를 시각화할 수 있을 것이다.
- **환경 및 데이터:** EXP-02와 동일한 Mac 내장 카메라 및 파란색 물체. 실시간 영상에서 물체를 다양한 속도와 거리로 움직였다.
- **변경한 변수:**
  - `collections.deque(maxlen=30)`으로 최근 중심점 최대 30개를 보관했다.
  - Exponential Moving Average(EMA) 방식으로 중심점을 보정했다.
  - `alpha = 0.3`을 사용해 새 측정값과 이전 보정값을 결합했다.
  - 저장된 중심점들을 선으로 연결해 최근 이동 경로를 표시했다.
  - 물체를 탐지하지 못하면 상태를 Searching으로 바꾸고 궤적 및 보정 좌표를 초기화하도록 했다.
- **ChatGPT의 제안:** 고정 길이 deque에 최근 좌표를 저장하고, EMA로 중심점을 부드럽게 만든 다음, 최근 좌표들을 `cv2.polylines`로 연결한다.
- **직접 수행한 작업:** 업데이트한 `object_tracker.py`를 실행하고 물체를 천천히/빠르게 움직이거나 화면 밖으로 이동시켰다. 다시 화면 안으로 가져오고 카메라와 물체 사이의 거리도 바꾸어 동작을 확인했다.
- **관찰한 결과:**
  - 천천히 움직일 때 중심점과 이동 경로가 물체의 움직임을 따라갔다.
  - 빠르게 움직일 때도 추적 표시가 계속 동작했다.
  - 물체를 화면 밖으로 숨겼다가 다시 보여줘도 다시 탐지됐다.
  - 카메라와 물체 사이의 거리를 바꾸어도 안정적으로 동작했다.
  - 사용자가 확인한 테스트 조건에서는 기본적인 탐지와 위치 표시가 안정적으로 유지됐다.
- **예상과 달랐던 점:** 단일 물체의 속도와 거리 변화에는 잘 대응했지만, 배경에 파란 빛이 있는 환경에서는 물체가 아닌 파란색 빛도 계속 탐지됐다. 파란색 물체를 동시에 두 개 보여주어도 한 개만 표시됐다.
- **해석 및 한계:**
  - EMA는 새 측정 좌표를 그대로 표시하지 않고 이전 보정 좌표와 섞어 작은 좌표 변화를 완화한다. `alpha=0.3`이면 새 좌표에 30%, 이전 보정 좌표에 70%의 가중치를 둔다. 작은 흔들림은 줄어들 수 있지만, 실제 움직임을 표시하는 데 지연이 생길 수 있다.
  - `deque(maxlen=30)`은 최근 30개 좌표만 유지한다. 새 좌표가 추가되면 가장 오래된 좌표가 자동으로 빠져나가므로 이동 경로의 길이를 제한하면서 오래된 위치가 계속 쌓이는 것을 막는다.
  - 현재 구현에서 deque는 좌표 이력을 보관하는 역할이고, 객체의 정체성을 판별하거나 여러 물체를 구분하는 역할은 하지 않는다.
  - EMA와 궤적은 중심점 표시를 부드럽게 보이게 하는 기법이지, 물체 탐지 자체의 정확도를 높이거나 다른 파란색 영역을 구분하는 기법은 아니다.
- **다음 단계:** 배경의 파란 빛이 탐지되는 원인을 확인하고, 한 프레임에서 여러 파란색 물체를 동시에 탐지할 수 있도록 윤곽선 처리 부분을 확장한다.

## EXP-04: 실제 환경에서 발견한 색상 오탐 및 단일 객체 선택 한계

- **상태:** 문제 관찰 완료, 원인 분석 및 개선 방향 수립. 개선 코드는 아직 구현·검증하지 않음.
- **실험 날짜:** 2026-11-05
- **목적:** 조명과 배경이 포함된 실제 환경에서 색상 기반 탐지가 어떤 한계를 보이는지 확인하고, 현재 코드가 여러 대상을 처리하는 방식을 이해한다.
- **질문 / 문제:**
  1. 뒤쪽에서 파란 빛이 들어오는 환경에서 실제 물체가 아닌 파란 빛도 계속 탐지되는 이유는 무엇인가?
  2. 파란색 물체 두 개를 동시에 보여주었을 때 왜 한 개만 추적되는가?
  3. 현재 구현이 이전 프레임에서 추적하던 물체와 다음 프레임의 물체가 같은 대상인지 구분하는가?
- **초기 가설:** 색상 범위만 사용하는 탐지 방식은 같은 색을 가진 조명과 물체를 구분하기 어려울 수 있다. 또한 코드가 가장 큰 윤곽선 하나만 선택한다면 여러 물체가 있어도 하나만 표시될 것이다.
- **환경 및 데이터:** EXP-03과 동일한 카메라 및 코드. 뒤쪽에서 빛이 들어오는 환경에서 파란색 물체를 사용했고, 파란색 물체를 두 개 동시에 카메라에 보여주는 조건도 확인했다.
- **변경한 변수:** 코드는 변경하지 않고 조명 환경과 화면에 보이는 파란색 물체 수를 바꾸어 관찰했다.
- **ChatGPT의 제안:** 현재 코드의 HSV 마스크 생성, 윤곽선 탐색, 최대 면적 윤곽선 선택 부분을 확인해 관찰된 현상과 연결한다. 개선은 모든 유효 윤곽선 탐지, 배경 오탐 필터링, 프레임 간 객체 연결 순서로 나누어 진행한다.
- **직접 수행한 작업:** 역광이 있는 환경에서 실행 결과를 관찰하고, 파란색 물체를 한 개 및 두 개 동시에 보여주어 표시 결과를 비교했다. 코드의 `cv2.inRange`, `cv2.findContours`, `max(contours, key=cv2.contourArea)` 부분을 함께 검토했다.
- **관찰한 결과:**
  - 실제 파란색 물체뿐 아니라 배경에서 들어오는 파란 빛도 탐지됐다.
  - 파란색 물체 두 개를 동시에 보여주었을 때 한 개만 추적 표시됐다.
  - 단일 물체의 이동 속도, 화면 이탈 후 재등장, 카메라와의 거리 변화에서는 앞선 테스트에서 안정적으로 동작했다.
- **예상과 달랐던 점:** 단일 물체의 이동 조건에서는 안정적으로 보였지만, 같은 색상의 배경 요소가 추가되거나 같은 색상의 물체가 여러 개 존재하면 현재 방식만으로는 대상을 구분할 수 없었다.
- **해석 및 한계:**
  - `cv2.inRange`는 각 픽셀의 HSV 값이 지정한 범위에 들어오는지를 검사한다. 파란색 물체인지 파란색 조명인지 의미를 이해하지 않으므로, 범위에 들어오는 배경 픽셀도 마스크에 포함된다.
  - Morphological Opening은 작은 흰색 노이즈를 제거하는 데 도움을 주지만, 넓게 이어진 파란색 빛 영역까지 자동으로 제거하지는 않는다.
  - `findContours`는 마스크에서 연결된 영역의 윤곽선을 찾을 수 있지만, 현재 코드의 `max(contours, key=cv2.contourArea)`는 그중 면적이 가장 큰 윤곽선 하나만 선택한다. 따라서 여러 파란색 영역이 있어도 하나만 bounding box와 중심점으로 표시된다.
  - 현재의 중심점 평활화와 deque 궤적 저장은 선택된 영역의 위치를 부드럽게 표시할 뿐, 프레임 사이에서 같은 물체인지 식별하지 않는다. 따라서 지금 단계의 구현은 색상 기반 영역 탐지와 단일 영역 위치 표시이며, 객체별 ID를 유지하는 다중 객체 추적은 아직 구현되지 않았다.
  - 면적이나 모양 조건을 추가하면 일부 오탐을 줄일 수 있지만, 파란색 조명과 실제 물체의 크기·형태가 비슷하다면 해당 조건만으로 확실히 구분할 수 있다고 보장할 수 없다.
- **다음 단계:**
  1. `max()`로 하나만 선택하는 부분을 바꾸어 여러 윤곽선을 모두 탐지하고 각각의 bounding box와 중심점을 표시한다.
  2. 파란색 조명 오탐을 줄이기 위해 면적, 종횡비, 형태 등 추가 조건을 검토하되, 실제 물체를 잘못 제외하는 경우도 함께 확인한다.
  3. 여러 물체가 동시에 탐지되면 이전 프레임의 중심점과 현재 중심점을 비교해 객체별 ID를 연결하는 간단한 방법을 구현한다.
  4. 두 물체가 서로 교차하거나 잠시 가려질 때 ID가 유지되는지 확인한다.

## EXP-05: HSV 채도·밝기 임계값 조절을 통한 반사광 억제

- **상태:** S/V 임계값 탐색 완료. 최적 후보값 확인. 다른 조명·물체 조건에서의 일반화 검증은 아직 필요함.
- **실험 날짜:** 2026-11-05
- **목적:** 파란색 물체와 옷 등에 반사된 파란빛이 함께 검출되는 문제를 줄이기 위해 HSV의 채도(S)와 밝기(V) 하한·상한을 조절한다.
- **질문 / 문제:** 색상(H) 범위만으로는 실제 파란색 물체와 파란색 반사광을 구분하기 어렵다. S와 V 조건을 추가로 제한하면 반사광은 줄이면서 실제 물체를 유지할 수 있을까?
- **초기 가설:** 반사광과 물체 표면의 채도 또는 밝기 분포에 차이가 있다면 S/V 임계값을 조절해 일부 반사광을 제외할 수 있을 것이다. 다만 임계값을 지나치게 높이면 물체의 일부 픽셀도 제외되어 마스크가 분리될 수 있다.
- **환경 및 데이터:** 기존 Mac 내장 카메라, OpenCV, 파란색 물체 및 옷에 반사된 빛이 보이는 환경. 실시간 카메라 화면을 보며 슬라이더 값을 변경했다.
- **변경한 변수:**
  - S min을 기본값 80에서 100 이상으로 높여 비교했다.
  - V max를 255에서 낮추며 비교했다.
  - V min을 높여 비교했다.
- **ChatGPT의 제안:** S min, V min, V max를 OpenCV 트랙바로 조절할 수 있도록 만들고, 한 번에 하나의 값만 바꾸어 물체 검출과 반사광 변화를 비교한다.
- **직접 수행한 작업:** 카메라를 실행한 상태에서 S min, V min, V max를 각각 조절하고, 파란색 물체가 유지되는지와 옷 등에 반사된 빛이 줄어드는지 관찰했다.
- **관찰한 결과:**
  - S min이 약 100일 때 반사광이 줄어들면서 실제 물체도 잘 탐지됐다.
  - S min을 100보다 더 높이면 물체 표면의 일부 영역이 제외되어 하나의 물체가 여러 조각으로 나뉘어 검출되기 시작했다.
  - V max를 조절했을 때는 관찰 환경에서 큰 차이를 확인하지 못했다.
  - V min은 약 99일 때 결과가 좋았다. 이보다 높이면 실제 물체의 일부가 검출되지 않는 등 탐지 성능이 저하됐다.
- **실험에서 선택한 기준값:** S min = 100, V min = 99, V max = 255. 이는 현재 테스트 환경에서 찾은 후보값이며 모든 조명·거리·물체 상태에 적용되는 보편적인 최적값은 아니다.
- **예상과 달랐던 점:** S min을 더 높이면 반사광이 계속 줄어들 것이라고 예상할 수 있지만, 실제로는 물체 표면의 일부도 함께 제거되어 물체 영역이 분리됐다. V max는 조절해도 눈에 띄는 차이가 크지 않았다.
- **해석 및 한계:**
  - S min을 높이면 채도가 낮은 픽셀을 제외할 수 있지만, 실제 물체의 반사·그림자·표면 차이로 인해 물체 내부에도 낮은 채도의 픽셀이 존재할 수 있다.
  - V min을 높이면 어두운 픽셀을 제외하지만, 물체의 어두운 부분도 함께 제거될 수 있다.
  - 현재 관찰 결과에서는 S min = 100, V min = 99가 반사광 억제와 물체 유지 사이의 균형이 가장 좋았다.
  - 이번 결과는 사용한 물체와 촬영 환경에서의 관찰이다. 다른 조명, 배경, 거리에서도 같은 값이 최선인지는 추가 검증이 필요하다.
- **다음 단계:** S min = 100, V min = 99를 기준으로 고정하고 최소 면적 및 bounding box 가로세로 비율 필터를 실험한다. 손으로 물체를 가렸을 때의 분리 영역과 Closing 커널 크기의 영향도 별도로 비교한다.

## 학습 질문 및 개념 정리

### 왜 `deque`를 사용했는가?

- 이동 경로를 그리려면 이전 프레임에서 계산한 중심점들을 일정 개수 보관해야 한다.
- 일반 리스트도 좌표를 저장할 수 있지만, 오래된 좌표를 직접 삭제하는 처리가 필요하다.
- `collections.deque(maxlen=30)`은 최대 길이를 지정할 수 있고, 길이를 초과해 새 항목을 추가하면 가장 오래된 항목을 자동으로 제거한다.
- 따라서 최근 30개 좌표만으로 궤적을 그리는 현재 요구에 간단하고 적합하다.
- 반드시 deque만 사용할 수 있는 것은 아니다. 리스트로도 구현할 수 있지만, deque는 양 끝에서의 추가·삭제가 효율적이고 고정 길이 이력을 관리하기 편리하다.

### 카메라는 하나인데 왜 OpenCV 번호가 여러 개인가?

- OpenCV의 숫자 인덱스는 물리적인 카메라 개수를 직접 세는 값이 아니라, 백엔드가 접근 가능한 영상 입력 장치를 인덱스로 열어보는 방식이다.
- 실제 장치 수와 인덱스가 직관적으로 일치한다고 가정하면 안 된다.
- 이번 환경에서는 인덱스 0은 프레임을 읽지 못했고 인덱스 1에서 프레임 수신에 성공했다.
- `isOpened()`와 `read()`를 함께 확인해야 실제 영상 입력이 가능한지 알 수 있다.

### 왜 처음에는 하나만 추적하도록 했는가?

- 하나의 대상만 다루는 것은 다중 객체 추적의 최종 목표가 아니라, 색상 탐지와 위치 계산을 먼저 확인하기 위한 학습용 범위였다.
- 다중 객체 추적에서는 여러 영역을 찾는 것뿐 아니라 프레임 사이에서 각 영역이 이전의 어떤 객체와 같은지 연결하고 ID를 유지해야 한다.
- 다음 단계에서 다중 객체 탐지와 객체별 ID 연결로 확장한다.

### 탐지(Detection)와 추적(Tracking)의 차이는 무엇인가?

- **탐지:** 현재 프레임에서 물체가 어디에 있는지 찾는 문제.
- **추적:** 시간에 따라 연속된 프레임에서 동일한 물체가 어떻게 이동하는지 연결하는 문제.
- 현재 구현은 매 프레임 파란색 영역을 다시 찾고 가장 큰 영역을 선택하므로, 이전에 선택한 대상의 정체성을 보장하지 않는다.
- 객체별 ID 연결과 가림 상황 처리는 아직 구현하지 않았다.
